# WorkPilot 路线图与依赖

更新日期：2026-10-05

本文只维护实施顺序、依赖与推进规则；当前状态见 [文档索引](README.md)，实际结果见各阶段完成记录。P13 已完成实现及本轮短时验证，正式验收仍待外部环境和用户体验。

## 3. 推荐执行顺序

~~~text
P00 → P01 → P02 → P03 → P04 → P05 → P06 → P07
                                               ↓
                                   P08 / P09 的实现
                                               ↓
                                      P10 → P11
                                               ↓
                                      P12 → P13
                                               ↓
                                      P14 → P15

P16 为后续扩展池，不能挤掉 P13 的首版验收。
~~~

当前以一个主要开发者推进，默认按表中顺序完成。P08、P09、P11 中部分工作可独立开展，但仅在确有并行开发资源时再拆分；这里的依赖图不是立即启用多个开发代理的指令。

## 4. 提前验证的难点

1. **Tauri 与双浏览器接入。** P00 先证明能读取并控制已授权网页，以及右侧工作区的呈现方案；P08 再完整实现。不能到界面完成后才发现浏览器连接不可用。
2. **三种模型协议。** P02 分别处理文本、图片、工具调用、结束条件和断流；接口地址相似不代表格式一致。
3. **“完整过程”所需事件。** P01 即定义工具、审批和子助手事件，避免 P06 为展示日志重写引擎。
4. **文件版本与脚本修改。** P04 开始考虑所有受管理写入的前后记录，P07 完成浏览与恢复。不能只给内置写文件工具做版本，漏掉终端和插件修改。
5. **退出与定时任务。** P00 验证进程生命周期，P06 实现隐藏与退出，P11 完成本地调度，保持同一条行为规则。
6. **随包环境。** P00 就核对可再分发组件、体积和离线安装条件；P12 完整打包，而不是最后要求用户自己安装开发环境。

## 5. 每阶段交付方式

阶段交付至少包括：

- 本阶段可运行的版本或独立验证程序。
- 对应需求和已实现项目清单。
- 自动检查结果，以及模拟验证与真实验证的区别。
- 用户可按步骤复现的体验清单。
- 未解决问题、影响范围和下一阶段是否受到影响。

普通技术实现按已确定方向继续推进。修改首版范围、改掉用户指定行为、切换桌面外壳或引入必须购买的服务时，先给用户可评估的方案。用户未要求逐阶段强制等待签字，不能自行增加这种流程。

## 6. 发生延误或验证失败时

将阶段标为进行中或待外部条件，写明具体原因及仍可推进的工作。不要把缺少真实模型账户、macOS 实机或签名条件写成“已通过”。

产品需求变化先更新 [需求基线](00-需求基线.md) 与 [决策记录](05-决策与待办.md)，再更新受影响的阶段、依赖和验收项，避免出现互相矛盾的计划。
